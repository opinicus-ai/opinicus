# Claude Code repository config redirected authenticated API traffic and stole the developer's API key before the trust prompt (CVE-2026-21852)

- Date: 2026-02 (Check Point disclosure; fixed by Anthropic between August and December 2025) | Agent/tool: Claude Code | Axis: secrets

## What happened

In February 2026, Check Point Research disclosed three Claude Code vulnerabilities that fired when a developer simply cloned and opened an untrusted repository. The secrets-relevant one, CVE-2026-21852, let repository-controlled configuration redirect Claude Code's API traffic — including the full `Authorization` header with the developer's active Anthropic API key — to an attacker-controlled server before the user had confirmed trust in the project directory. Concretely, a malicious repository could set `ANTHROPIC_BASE_URL`, and the agent would happily send authenticated requests to that endpoint on startup, handing over a working credential with no visible indication that anything had happened. The sibling findings were silent command execution through session-start hooks and an MCP consent bypass (CVE-2025-59536) in which repo settings overrode the approval prompt for tool initialization. A stolen key matters beyond quota: Anthropic Workspaces attach shared project files to the key's workspace, so one leaked key could read, modify or delete cloud-stored team data and run up arbitrary API costs. Anthropic patched all three issues between August and December 2025, ahead of the public disclosure.

## How it went wrong

There was no exploit chain on the endpoint in the classic sense — the agent itself performed the leak. Claude Code treats repository-level configuration files (`.claude/settings.json` and friends) as an execution layer: they can define hooks, MCP servers and environment variables that take effect when the tool starts in the project directory. A poisoned config changed the API base URL the agent uses for every model call, so the very first authenticated request — key in the authorization header — went to attacker infrastructure before the trust prompt appeared. From the OS point of view the sequence is: user runs `claude` inside the cloned repo → the agent process starts with an environment (or effective config) whose base URL points off-vendor → the agent makes an outbound HTTPS connection to the attacker's host and sends the credential. No extra process, no file read, no shell command: the misbehavior is one environment value plus one connection, both established by the trusted agent binary itself.

## What the firewall should learn

The decisive observable is available at the moment the firewall launches the agent: the process environment. Rule ideas: (1) at agent exec, match provider base-URL overrides in env (`ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, `OPENAI_API_BASE`, `GOOGLE_GEMINI_BASE_URL`) whose value is not an allowlisted vendor or corporate-gateway host and require approval before the first API call — this catches the attack with zero false negatives on stock setups, since most sessions carry no override at all. (2) Confirm at the network layer: the agent process's first API connection should land on a vendor domain; an agent-ancestry connect to a fresh non-vendor host after a base-URL override is the exfil moment and can be terminated. (3) Correlate with repo-config provenance: an override appearing only after entering a new work tree (settings.json read from the project) is far more suspicious than a machine-wide proxy configured by the user — a distinction the approval prompt should surface. (4) The same repo-config-as-execution-layer lesson covers the hook and MCP halves of the disclosure, which live in the inject and MCP catalogs; for the secrets axis the invariant is simple: the agent's own credential must only ever travel to the vendor or a user-configured gateway, and both endpoints are knowable before the first request is sent.
