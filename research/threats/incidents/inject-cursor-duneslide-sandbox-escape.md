# DuneSlide: zero-click prompt injection broke Cursor's command sandbox and became unsandboxed RCE (CVE-2026-50548, CVE-2026-50549)

- Date: 2026-07 (Cato AI Labs disclosure; reported 2026-02-19, CVEs assigned 2026-06-05, fixed in Cursor 3.0) | Agent/tool: Cursor IDE 2.x | Axis: inject

## What happened

Cato AI Labs discovered two critical remote-code-execution vulnerabilities in Cursor IDE, each scoring 9.8 CVSS, that turned a zero-click prompt injection into full system compromise. The entry point required no user interaction: an innocuous MCP server response or a poisoned web-search result ingested by the agent carried the injected instructions. Cursor 2.x executes agent terminal commands inside a sandbox by default and without prompting, precisely to stop a prompt injection from becoming an RCE. Both flaws broke that assumption. In the first, the optional `working_directory` parameter of the `run_terminal_cmd` tool was blindly added to the sandbox's allowed-write list, so injected text could steer the agent to aim commands at any path outside the project. In the second, the agent was instructed to create a symlink inside the project pointing to an outside target; Cursor's path canonicalization has a fallback that treats unresolvable paths as the in-project symlink path, so a deliberately write-only symlink let the Write tool modify files far outside the project root. In both attacks the target was Cursor's own sandbox helper binary (`cursorsandbox`); once overwritten, every subsequent injected command ran without sandbox restrictions. Cato also named `~/.zshrc`, `~/.zshenv` and `~/Library/LaunchAgents` as reachable targets. Cursor initially rejected the reports — its threat model did not account for MCP server misuse — then re-opened them; the working-directory fix shipped with Cursor 3.0 on 2026-04-02 and the link-target fix was confirmed by 2026-06-01.

## How it went wrong

The distinctive move is that plain text was the exploit primitive: the injection did not attack the LLM's instructions but the guardrail code's inputs. The sandbox derived its write boundary from tool parameters that the model fills in, and the injection controls what the model fills in — so setting `working_directory` to `/Applications/Cursor.app/Contents/Resources/app/resources/helpers` made the sandbox itself legalize writes to the sandbox binary. The symlink variant weaponized a defensive mechanism: canonicalization exists to catch out-of-bounds writes, and its failure fallback (use the symlink path when the target cannot be resolved) was forced by creating a write-only symlink, flipping the check to the wrong path. The OS-level sequence: agent writes (via the Write tool or a shell redirect) land on the `cursorsandbox` executable; the next "sandboxed" terminal command execs the trojanized helper unsandboxed; the attacker holds a shell on the developer machine and, through connected integrations, on associated SaaS workspaces. Both paths end with the agent's own process tree executing attacker code with no exploit against a classic parsing bug — the injection simply relocated or re-scoped the allowed write.

## What the firewall should learn

The sandbox trusted a boundary that the injection could steer; an external monitor must derive the boundary itself from its own session state. Concretely: (1) the `cwd` field of every `exec` event is the first primitive — a command under agent ancestry whose working directory resolves outside the session work tree recorded at launch is `approval_required`, because a sandbox-scoped write boundary is exactly the thing being moved; (2) symlink relocation is argv-visible today — `ln -s` with a target outside the work tree and the link inside it gates immediately, and later writes through a remembered linkpath escalate (pairs with evade-13's link rule); (3) writes aimed at the agent's own install tree (the `/Applications` helper, the npm global prefix, shell startup files, LaunchAgents) are never a developer task from agent ancestry and deserve `deny`; (4) the general rule: the firewall's notion of "inside the project" must come from its own observations at launch, never from parameters the agent passes to its own tools — this incident is the worked example of why. All of layers 1–3 need only `exec` plus session state.
