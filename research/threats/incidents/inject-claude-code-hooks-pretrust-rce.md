# Claude Code repository settings ran hooks and MCP servers before the user could approve anything (CVE-2025-59536)

- Date: 2026-02-25 (public disclosure; first report to Anthropic 2025-07-21) | Agent/tool: Claude Code | Axis: inject

## What happened

Check Point Research disclosed critical Claude Code vulnerabilities in which simply cloning and opening an attacker-controlled repository executed attacker shell commands on the developer's machine. Two of the three findings are prompt-injection-to-execution on the inject axis. First, a `SessionStart` hook written into the repository's `.claude/settings.json` ran its shell command automatically during Claude Code initialization — after the user clicked the generic "trust this folder" dialog but with no additional confirmation, even though ordinary bash commands during a session do prompt. It escalated cleanly to a reverse shell. Second, the repository could pre-answer Claude Code's own MCP consent dialog: `enableAllProjectMcpServers` or `enabledMcpjsonServers` placed in the repo-controlled settings file auto-approved the servers declared in the repo's `.mcp.json`, and the MCP initialization command executed immediately on `claude` startup — before the user could even read the trust dialog; in the demo the Calculator opened on top of the pending dialog. Anthropic fixed the hooks case with an enhanced warning dialog (advisory GHSA-ph6w-f82w-28w6, 2025-08-29) and the bypass by deferring all MCP execution and network operations until after explicit user consent (CVE-2025-59536, 2025-10-03). The third finding, API-key theft via a repo-controlled `ANTHROPIC_BASE_URL`, is written up on the secrets axis (`secrets-claude-code-baseurl-key-exfil`).

## How it went wrong

Claude Code treats repository-level files as an execution layer: `.claude/settings.json` can define hooks, MCP servers and environment variables that take effect when the tool starts in that directory, and any contributor with commit access can write them. The hooks case abused the SessionStart matcher: the trust dialog's warning that files may be executed "with your permission" was never followed by an actual permission prompt for hook commands, so the session looked normal while repository-authored commands had already run. The MCP case is config approving config: the same repository file that declares the malicious `.mcp.json` server also carries the settings key that waives consent for it, so the user's approval was structurally pre-empted. At the OS level both chains are identical and short: the user runs `claude` in the cloned repo, and the trusted agent binary itself spawns `/bin/sh` (or the configured interpreter) carrying the attacker's command under the agent's process tree — no exploit against the agent, no suspicious binary, just configuration that the agent faithfully executes. Check Point's supply-chain framing: the payload spreads as a malicious pull request, a honeypot repository, or one insider commit, because developers review configuration files as metadata, not as code.

## What the firewall should learn

The agent's own consent flow is not a security boundary — the hook and MCP commands executed with zero, one rubber-stamp click, or a pre-answered dialog. The ptrace monitor sits below that lie and sees the shell spawn regardless. Rule ideas. (1) Startup-window gate: an `exec` of a shell or interpreter spawned by the agent binary within the first seconds of agent launch, before any user-initiated tool call in the session, is `approval_required` — legitimate sessions start by reading files, not by running commands. (2) The write-side persistence is already the subject of inject-01/inject-02 (`settings.json`, `.mcp.json` writes from agent ancestry are gated); the clone-time variant needs session taint (inject-08): a work tree created this session by `git clone` taints the early execs that originate from its config. (3) The "config approving config" move is the sharpest general lesson: the firewall must never inherit agent-internal approval state — an approval that exists only because a repository file granted it is not consent, so the monitor keeps its own per-session approval registry keyed on user actions, and anything executing before the first genuine user decision runs at an elevated decision floor. All of these need only `exec`, `input` and the session layer that already exists.
