# Shai-Hulud: The Third Coming compromised @bitwarden/cli and drained every cloud secret manager it could reach

- Date: 2026-04-22 | Agent/tool: @bitwarden/cli@2026.4.0 npm package, Bun-loaded payload, local AI CLIs (claude, gemini, codex, kiro, aider, opencode) | Axis: secrets

## What happened

On April 22, 2026, a trojanized `@bitwarden/cli@2026.4.0` was published to npm and stayed live for roughly 1.5 hours (5:57 PM to 7:30 PM ET) before being deprecated. The Bitwarden CLI is the command-line front end of a widely used open-source password manager, and teams wire it into CI/CD pipelines to inject secrets at build time — so a compromised `bw` is a skeleton key to every secret the machine and its cloud accounts can reach. The package shipped a `preinstall` hook (`node bwsetup.js`) that downloaded the Bun 1.3.13 runtime from GitHub Releases and used it to execute a ~10 MB obfuscated payload (`bw1.js`). The payload ran seven parallel credential collectors: a filesystem sweep of hotspot files, an environment dump, a GitHub Actions runner memory scrape, and — novel at this scale — bulk SDK enumeration of AWS Secrets Manager, AWS SSM Parameter Store, GCP Secret Manager and Azure Key Vault with whatever ambient credentials the machine had. Loot was AES-256-GCM encrypted with the key wrapped under an embedded RSA public key, then committed to fresh Dune-themed public repositories ("Shai-Hulud: The Third Coming") on the victim's own GitHub account. A module codenamed "butlerian jihad" probed `$PATH` for six AI coding CLIs and invoked each with a "respond with Hello" prompt to confirm it was authenticated before planting persistence in `~/.bashrc` and `~/.zshrc`. The campaign was connected to the earlier Checkmarx GitHub Actions breach; a working npm token let it re-publish poisoned tarballs of every package the victim could publish.

## How it went wrong

Initial access was CI, not the victim machine: Bitwarden's publish pipeline (OIDC trusted publishing with `id-token: write`) was subverted after the Checkmarx Actions compromise, so the malicious 2026.4.0 tarball went out through the project's own release identity. On every install, the chain was `npm install` → `preinstall: node bwsetup.js` → Bun download from github.com/oven-sh/bun/releases → `bun bw1.js`. The collectors then did, in OS terms: reads of `~/.ssh/id_rsa`, `~/.npmrc`, `~/.aws/credentials`, `~/.gitconfig`, `~/.kube/config`, `.env` and friends (Endor Labs notes the exact macOS/Linux path list is inferred from decoded patterns); an `execSync` shell dump plus `process.env`; on GitHub Actions Linux runners a pipe of an embedded Python payload through `sudo python3 | tr -d '\0' | grep -aoE '"[^"]+":{"value":"[^"]*","isSecret":true}'` to lift runner secrets out of memory while deliberately skipping `github_token` to dodge auto-revocation; and bundled `@aws-sdk/client-secrets-manager`, `@aws-sdk/client-ssm`, `@google-cloud/secret-manager` and `@azure/keyvault-secrets` calls that listed every secret and fetched each value. C2 was a GitHub commit-search dead-drop (`LongLiveTheResistanceAgainstMachines` plus an RSA-signed `beautifulcastle` channel), so command and control blended into normal api.github.com traffic. The butlerian-jihad module exec'd `claude`, `gemini`, `codex`, `kiro`, `aider` or `opencode` with the hello-probe prompt, and appended a gzip+base64 heredoc hook to both shell RC files when a tool answered. A Russian-locale check, CI fingerprinting, signal no-ops and console silencing rounded out the anti-analysis.

## What the firewall should learn

Every step after `npm install` is exec-visible to a ptrace monitor. Rule ideas: (1) bulk secret-manager drain — `aws secretsmanager list-secrets` / `ssm get-parameters-by-path` / `gcloud secrets list` / `az keyvault secret list` followed by per-item value fetches from agent or install ancestry is harvesting even when each individual call looks like a benign `get-secret-value`; escalate the existing single-read approval to deny when the pattern is enumerate-then-fetch-all. (2) The stager's Bun download-and-exec from a package directory is the process.exec.from-temp / decoder-chain shape and should terminate under install ancestry. (3) An AI CLI exec'd from a package-install subtree with a hello-probe prompt is an unattended nested agent — the argv (`"Hey! Just making sure you're here…"`) is fully visible and unlike any developer command. (4) The runner-memory scrape pipes `sudo python3` through `tr`/`grep` — install ancestry plus sudo is already a terminate-grade combination. (5) Honest limit: the SDK-based cloud collectors never spawn a CLI process, so the exec layer sees nothing of the AWS/GCP/Azure drain itself; that half needs the network-egress correlation (fresh list-and-get conversations to vendor APIs from a freshly installed subtree) or an HTTP-layer observable the current monitor does not have.
